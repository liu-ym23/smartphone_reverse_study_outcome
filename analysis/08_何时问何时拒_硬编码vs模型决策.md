# 豆包何时询问用户 / 拒绝操作——硬编码条件 vs 模型决策

> 只回答一个问题：**在什么条件下豆包会问用户或拒绝执行**，以及这个条件是**写死在客户端代码里的**还是**服务端模型自己判断的**。
> 不讨论卡片怎么渲染、协议长什么样。

---

## 一句话总结

**客户端代码里写死的拦截条件极少（且大多只在锁屏或非 Omni 路径生效）；实际遇到的大部分"问用户/拒绝"都是服务端模型的判断。**

---

## 第一部分：写死在客户端代码里的条件

以下是反编译代码中找到的、**不依赖模型判断**的硬性条件。满足条件就必然触发，模型无法绕过。

### 1. 锁屏认证（intent 路径）

**文件**：`execution/security/a.java`（AuthenticationProcessor）

**写死的条件**：
```java
// 以下条件全部满足时，intent 被拦截并要求用户认证：
if (isDeviceLocked == true                    // 设备处于安全锁屏状态
    && sessionAuthPass == false               // 本次会话尚未通过认证
    && isComplexTask == false                 // 不是 Omni 复杂任务
    && o_skip_authentication != "1"           // 服务端没下 发跳过标记
    && intentHasPolicy(type 1|2|3))           // intent 策略表类型为需认证
→ 弯出认证界面（声纹/生物识别），用户通过后才执行
```

**关键**：
- 策略表 `intent_execute.json` 是写死的（161 条，每 intent 一个 type）
- 但**解锁态下全部放行**（`isDeviceLocked == false` → 直接 return null）
- 本设备**无安全锁** → 此条件永远不触发

**结论**：对解锁态设备，**这条硬编码规则形同虚设**。

---

### 2. 任务冲突拒绝

**文件**：`autoaction/intent/AutoActionIntent.java` 行 985+

**写死的条件**：
```java
if (hasOngoingTask() == true       // 已有一个 Omni 任务在跑
    && newTask.isComplex == false) // 新任务不是 Omni 复杂任务
→ 新任务被拒绝（返回冲突结果）
```

**关键**：这是**唯一一条在解锁态也生效的端侧硬拦截**。但只阻止 Omni 任务重复，不阻止 intent 路径并行。

---

### 3. 提示词敏感内容（Omni 任务入队时）

**文件**：`session/state/a/k.java` 行 222-244

**写死的条件**：
```java
// 任务文本经过端侧小模型(pico_content_security)检查：
if (checkPrompt(userTask) == 不通过)
→ 任务直接失败，错误信息 "query includes sensitive content"
```

**关键**：
- **调用点是写死的**（每个 Omni 任务入队时必查）
- 但**判定是模型**（pico 小模型推理，不是关键词匹配）
- 命中概率取决于模型训练，不可从代码预知哪些词会触发

---

### 4. 截图级 robots 策略（Omni 每步截图时）

**文件**：`common/api/space/BaseDisplayOperatingSpace.java` 行 295+

**写死的条件**：
```java
// 每次截图前查询 AGRP 策略：
if (topActivity 的 AGRP 策略中 screenshot_disable == true
    || global_disable == true)
→ 截图失败（Invisible），模型看不到屏幕，任务无法继续

if (input_disable == true)
→ 标记为 Inoperable（但 Omni 主路径不检查此标记，不影响注入）
```

**关键**：
- 查表逻辑写死，**但表的内容不写死**（来自 content provider，由 app 声明或云端更新）
- **screenshot_disable 和 global_disable 会真正阻止 Omni 任务**（模型没截图就看不到屏幕）
- input_disable 在 Omni 主路径**不阻止注入**（只标记，不检查）

---

### 5. FLAG_SECURE 检测（Omni 每步截图时）

**文件**：`platforms/tools/internal/b/b.java`（ReflectedScreenCapture）

**写死的条件**：
```java
if (screenshotBuffer.containsSecureLayers() == true)
→ 截图结果标记为 ContainsSecure，页面内容不交给模型
```

**关键**：系统 API 判定，完全写死。银行/支付类 app 设置了 FLAG_SECURE 的页面无法被感知。

---

### 6. 循环防护（仅脚本路径，Omni 不经过）

**文件**：`agents/vlm/models/impl/e/c/b.java`

**写死的条件**：
```java
if (同一能力操作重复次数 >= 10)
→ 阻断后续执行
```

**关键**：阈值 10 写死。但此检查只在脚本路径（StandardModelScriptStep→StepExecutor）中调用，**Omni 主路径不经过**。

---

### 7. 每步五连检（仅脚本路径，Omni 不经过）⚠️

**文件**：`agents/vlm/models/impl/e/c/f.java`

以下五个条件**只在脚本路径**的 StepExecutor 中逐个检查，**Omni 主路径完全不经过**（字节码交叉引用已证实唯一调用点为 `l.java` StandardModelScriptStep）：

| 条件 | 写死的判定 | Omni 主路径是否检查 |
|---|---|---|
| app 在黑名单 | 包名比较（云下发+用户授权合成） | **❌ 不检查** |
| 目标 app 正在执行敏感操作 | 系统事件通知（23 种枚举写死） | **❌ 不检查** |
| 出现权限弹窗 | Activity 组件名精确匹配 | **❌ 不检查** |
| 免密支付页面 | 包名/Activity 查云端表 | **❌ 不检查** |
| robots input_disable | AGRP 策略查表 | **❌ 不检查** |

**结论**：这五项在 Omni 主路径上全部不存在。Omni 任务（即"手机任务"）不受这些硬编码条件约束。

## 第二部分：服务端模型的判断（客户端代码不控制）

以下是**模型/服务端自己决定**的"问/不问/拒/不拒"，客户端只是被动执行或渲染。

### 8. 是否下发 intent（服务端决定）

**机制**：模型决定调不调工具。如果模型判断"不应执行"，它直接回复文本，不发任何 intent。

**实测证据**：
- 删联系人：模型两次都没调 Contacts_Delete（端侧零执行痕迹）
- 微博未授权：模型直接回"没有权限"
- 小红书：模型尝试后被告知"AGRP 未加入"

**客户端能做的**：**无**。客户端无法强制模型调用某个工具。

---

### 9. needConfirm 标记（服务端决定）

**机制**：模型在 intent 消息上附带 `needConfirm=true` + 确认文案，客户端渲染确认框。

**影响因子**：
- **风险偏好设置**（上行给服务端作上下文）：
  - "确认优先"(1) → 模型几乎都加 needConfirm
  - "自主优先"(3) → 模型几乎不加
- **任务性质**：破坏性操作更容易触发
- **上下文**：对话历史、用户之前的偏好

**客户端能做的**：**无**。客户端只是展示服务端发的确认框，不能自己决定"这个操作要确认"。

**实测数据**：
- 自主优先 + 12 项任务 → 零确认
- 确认优先 + 打开app → 确认框
- 确认优先 + 删邮件 → 确认框（含"不可恢复"警告）

---

### 10. CallUserStep（服务端 Omni 模型决定）

**机制**：Omni 执行中，模型下发 `CallUserStep` 暂停执行等待用户回答。

**模型在什么情况下选择 CallUserStep**：
- 遇到权限弹窗（从截图识别出 GrantPermissionsActivity）
- 任务文本明确要求"问用户"
- 信息不足需要用户补充（如"发哪个视频？"）
- 遇到不确定的操作

**客户端能做的**：**无**。CallUserStep 是服务端下发的步骤类型，客户端只是执行（暂停+渲染选项）。

**实测数据**：
- 微博权限弹窗 → 模型选择 CallUserStep（"始终允许/拒绝"）
- 任务要求"问我要不要打开" → 模型在正确时机 CallUserStep
- B 站评论未指定视频 → 模型 CallUserStep（三选一 + 链式追问）

---

### 11. 服务端安全策略（AGRP 准入/黑名单）

**机制**：服务端维护一份 app 准入名单。未加入的 app 直接拒绝下发任务。

**实测数据**：
- 小红书 → "根据「屏幕自动化操作声明」协议...暂未允许" → 10 秒失败
- 哔哩哔哩 → 正常执行
- 微博（撤销授权后）→ "没有自动操作微博的权限"

**客户端能做的**：**无**。这是纯服务端判断。

---

### 12. AskUser/澄清（服务端模型决定）

**机制**：模型判断任务信息不足，直接回复澄清文本（不调工具）。

**实测数据**：
- "发消息" → "你想通过什么渠道发送消息呢？"
- 乱码输入 → "表述语义不太清晰，请重新说明"

**客户端能做的**：**无**。

## 第三部分：总结矩阵

| 条件 | 谁决定 | 解锁态+Omni 是否生效 | 实测验证 |
|---|---|---|---|
| 锁屏认证 | **代码写死**（策略表+锁屏状态） | ❌ 无安全锁=永远不触发 | ✅ 锁屏无安全锁直接过 |
| 任务冲突 | **代码写死** | ✅ 生效 | 代码确认 |
| 敏感内容 | **代码写死调用点，模型判定** | ✅ 生效 | 未触发（正常任务） |
| robots screenshot_disable | **代码写死查表，表内容来自 app** | ✅ 生效（截图失败→任务停） | 未触发（测试 app 未禁） |
| FLAG_SECURE | **代码写死**（系统 API） | ✅ 生效 | 未触发（无 secure 页面） |
| 循环防护(≥10次) | **代码写死** | ❌ 仅脚本路径 | 代码确认 |
| 黑名单/敏感操作/权限弹窗/支付页 | **代码写死** | ❌ 仅脚本路径 | **实测：Omni 删联系人未被拦** |
| 是否下发 intent | **模型** | — | ✅ 删联系人模型不下发 |
| needConfirm | **模型**（受风险偏好影响） | — | ✅ 确认优先→弹框；自主→不弹 |
| CallUserStep | **模型** | — | ✅ 权限/歧义/任务要求均触发 |
| AGRP 准入 | **服务端** | — | ✅ 小红书被拒 |
| AskUser 澄清 | **模型** | — | ✅ "发消息"触发 |

## 第四部分：直接回答你的问题

**Q: 豆包何时会询问用户？**

| 触发 | 决定者 | 你能从代码里预测吗 |
|---|---|---|
| 弹确认框"确定要XX吗？" | **服务端模型**（needConfirm） | **不能**——取决于模型判断+风险偏好设置 |
| 执行中暂停问"选哪个？" | **服务端模型**（CallUserStep） | **不能**——模型自己决定何时需要问 |
| 回复"你想通过什么渠道？" | **服务端模型**（AskUser） | **不能**——模型判断信息不足 |
| 要求声纹/指纹认证 | **客户端代码**（锁屏+策略表） | **能**——但仅限安全锁屏状态 |

**Q: 豆包何时会拒绝操作？**

| 触发 | 决定者 | 你能从代码里预测吗 |
|---|---|---|
| "没有操作XX的权限" | **服务端**（AGRP 准入/用户授权） | **部分能**——AGRP 未加入的 app 必拒 |
| 任务入队时敏感内容检查 | **客户端代码调用+端侧模型判定** | **不能**——pico 模型推理结果不可预知 |
| 同类任务冲突 | **客户端代码** | **能**——hasOngoingTask() 必拒 |
| 截图被 robots 禁止 | **客户端代码**（查 AGRP 表） | **能**——app 声明了 screenshot_disable 必拦 |
| FLAG_SECURE 页面 | **客户端代码**（系统 API） | **能**——有 secure flag 的页面必拦 |
| "删除操作不可恢复" | **服务端模型**（needConfirm） | **不能** |

**Q: 哪些是写死的，哪些是模型的选择？**

**写死的（客户端代码不依赖模型）**：
1. 安全锁屏时的 intent 认证（但无安全锁=不生效）
2. 任务冲突（hasOngoingTask）
3. 截图时 robots screenshot_disable 查表
4. 截图时 FLAG_SECURE 检测
5. 循环防护 ≥10 次（仅脚本路径）

**模型的选择（客户端无法控制）**：
1. 要不要调这个工具（还是直接拒绝）
2. 要不要加 needConfirm 让用户确认
3. 要不要用 CallUserStep 暂停问用户
4. 要不要回复澄清文本
5. 要不要把某个 app 加入黑名单

**写死了但只在脚本路径生效（Omni 不经过）**：
1. 黑名单包名比较
2. 敏感操作事件检测（23 种）
3. 权限弹窗组件名匹配
4. 免密支付页面查表
5. robots input_disable 检查

## 附：脚本路径 vs Omni 主路径——两条执行路径详解

### 什么是脚本路径

客户端**本地执行预建脚本**。服务端说"这个任务用脚本 X 执行"，客户端跑一段 JavaScript（通过 vmsdk JsWorker），脚本里写好了每一步操作（打开 app → 点击 → 输入 → 提交）。**每一步执行前经过 SecurityCheck 五连检。**

适用于已知标准流程（如"打开某 app"），执行快、不需 AI 逐步决策。

### 什么是 Omni 主路径

**服务端大模型逐步决策**。流程：
1. 客户端截图虚拟屏 → 发给服务端
2. 服务端 AI 看截图，决定下一步（"点击坐标 (441,434)"）
3. 下发 `GUI_Action` 指令给客户端
4. 客户端直接注入点击（不检查内容）
5. 截图新状态 → 发回服务端
6. 循环直到任务完成

**每步不经过 SecurityCheck**——服务端说点哪就点哪。

### 代码层面的分叉点

```
服务端下发步骤类型：
  ├─ type = "script" → ScriptStepParser(d/e) → StandardModelScriptStep(l)
  │    → StepExecutor(e/b/e) 带SecurityCheck(e/c/f) → 逐步检查+执行
  │
  └─ type = "action" → StdModelStepParser(d/f) → ActionedStep(e)
       → session/c.c() → step.b() → 直接注入（无检查）
```

字节码交叉引用证据：SecurityCheck 接口(e/c/e)的全插件唯一调用方 = StepExecutor(e/b/e)；StepExecutor 的唯一构造点 = StandardModelScriptStep(l)。ActionedStep(e) 和 session/c.c() 不引用 SecurityCheck。

### 实际影响

| | 脚本路径 | Omni 主路径 |
|---|---|---|
| 每步安全检查 | ✅ 五连检（黑名单/敏感事件/权限弹窗/支付页/robots） | ❌ 无 |
| 循环防护 | ✅ ≥10次阻断 | ❌ 无 |
| 用户日常任务占比 | 少（已知简单流程） | **多（复杂任务都走这条）** |
| 删联系人实测 | 未测试（走 Omni） | agent 直接点确认框，删除完成 |
| 权限弹窗实测 | 未测试 | agent 选择 CallUserStep 问用户（服务端模型行为，非端侧代码） |

## 修正：三层分类（不是两层）

此前把"服务端规则"和"模型判断"混为一谈，应分为三层：

| 层 | 本质 | 例子 | 可预测性 |
|---|---|---|---|
| **客户端代码**（硬编码） | 反编译代码里的 if-else | 锁屏认证、任务冲突、FLAG_SECURE、循环≥10次 | **完全可预测**（读代码就知道） |
| **服务端规则**（确定性查表） | 服务端数据库查询，非黑即白 | AGRP 准入（小红书不在名单→必拒）、用户授权（撤销→必拒） | **可预测**（知道名单就能判断） |
| **模型判断**（AI 决策） | 大模型根据上下文推理，概率性 | needConfirm、CallUserStep、AskUser | **不可预测**（无法从代码推断何时触发） |

## 补充：敏感内容检查的完整判定链（含 fallback）

```
任务文本
  │
  ▼
① AI 模型推理（pico_content_security，端侧 DSP/NPU）
  ├─ 返回含 "security" 类别 → 放行（风险 0）
  ├─ 返回不含 "security" → 拦截（风险 3）
  └─ 返回 null（模型不可用/推理失败）→ 走 fallback ↓
  │
  ▼
② 词表匹配（SensitiveWordFilter，云端下发）
  ├─ 匹配到敏感词 → 拦截（风险 1）
  └─ 未匹配 / 词表为空 → 放行（风险 0）
```

**词表数据**：云端经 `content://com.obric.securityserver.settings/.../settings_sens_words` 下发，存储在 `/data/misc/security/guard/`，格式为 `Map<类别名, Set<敏感词>>`。无 root 不可读内容。

**源码**：
- 调用点+fallback 逻辑：`platforms/tools/security/d.java` 行 150-175（`inferPromptRiskType` 方法）
- AI 推理：`securityguardkit/SecurityGuardKitManager.java` 行 105+（`inferSensitiveContent`）
- 词表加载：`securityguardkit/wordfilter/b.java` 行 268+（从 `ObricSecurityGuardStub.getSecurityPolicy` 读取）

## 补充：敏感词表的实际内容（部分获取）

### 词表存储结构

securityserver APK 的 `assets/` 中打包了两份：

| 文件 | 版本 | 加密 | 内容 |
|---|---|---|---|
| sens_words.json | 0 | **明文** | 7 个类别，**全部为空**（占位模板） |
| sens_words_2.json | 1 | AES-GCM（硬件密钥） | **~30KB 加密词数据**（实际词表） |

### 明文版（v0）的 7 个类别名（完整）

```
abuse            （虐待）
dangerous_behavior（危险行为）
discrimination   （歧视）
drugs            （毒品）
negative_leaders （负面领导人）
politics         （政治）
pornography      （色情）
```

每个类别当前 0 个词——这是**类别框架**，实际词条在加密版中。

### 加密版（v1）解密流程

```
服务端下发 JSON:
  { version: 1, encrypt_type: "platform", platform: "SM8850",
    public_key: <Base64>, words_key: <Base64>, words_cipher: <42KB Base64> }

客户端解密:
  ① 根据 SOC 型号选密钥 ID（SM8850 → -983037）
  ② 调框架 API ObricSecurityGuardStub.a(context, clientId, publicKey, wordsKey, bundle)
     → 硬件 Keystore 派生 AES 密钥
  ③ AES/GCM/NoPadding 解密 words_cipher → 得到明文 Map<类别, Set<词>>
```

**无 root 无法解密**（密钥在硬件 Keystore 中，每个 SOC 型号不同）。

### 实际状态

logcat 显示 `SensitiveWordFilter: 解析敏感词表错误` —— Doubao 进程中的词表解密**正在失败**，意味着 fallback 词表匹配**可能不工作**。如果 AI 模型（pico）也不可用，敏感内容检查会直接放行（return 0）。

## 补充案例：B站手机号登录被阻止（login1-3.png）

**任务**："打开哔哩哔哩，用手机号13800138000登录"

**执行过程**：
1. Agent 打开 B站 ✅
2. 导航到手机号登录页 ✅
3. 准备输入手机号时 → **"检测到当前提交账号凭证操作存在风险，请手动操作。"** + 接管按钮

**分析**：
- logcat 无任何端侧安全检查触发（无 SecurityCheck、无敏感事件、无权限弹窗检测）
- 判定发生在**服务端 Omni 模型**——模型从截图中识别出登录页面，判断提交账号凭证风险过高
- 这是**模型决策**，不是硬编码规则
- 模型没有选择 CallUserStep 问用户确认，而是直接放弃并要求接管

**结论**：账号登录/凭证提交场景由**服务端模型自行判断风险**，无端侧硬编码拦截。模型对此类场景的态度是**直接拒绝而非确认后执行**。
