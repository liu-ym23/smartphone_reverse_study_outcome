# 硬门禁"判定主体"对照表 —— 谁判定、用什么信号、在哪执行

> 回答核心问题：每一项硬门禁的判定是**模型判断**还是**代码判断**？若是代码，数据信号从哪来？
> 结论先行：**全部为代码判定（非模型）**；其中"敏感内容检查"用端侧小模型（非对话 LLM），其余均为字符串/集合比较或系统通知。

## 逐项对照

### 1. "目标 app 正在访问敏感设置"（敏感设置操作检测）——【纯代码 + 系统显式埋点通知】
- **信号来源：不是猜测、不是截图识别，是 ROM 定制系统应用主动上报的事件**。
- 链条：
  1. ROM 修改过的系统应用（设置/信息/文件管理/电话等）在执行**23 种硬编码敏感操作**时调用框架 binder API `bdSettingsEventStart/End` 上报——事件枚举写死在 `ObricSettingsEvent`（classes4）：短信删除、联系人删除、通话记录删除、文件删除、笔记删除、照片删除、故事删除、保险箱删除、录音删除、日历删除、相册删除、清除应用数据、垃圾清理、**删除密码/指纹/面部**、恢复出厂、卸载应用、重启、关机、安装未知应用、关闭地震预警、关闭网页预警。
  2. system 侧 `ObricSecurityGuardManager`（obric-services.jar）按调用方包名广播给所有注册的 `IObricSettingsEventObserver`。
  3. 豆包插件 `BDSettingsEventObserver` 收事件缓存 `pkg→Set<eventId>`（ConcurrentHashMap）。
  4. **GUI 每步执行前** `checkSettingsEvent(虚拟屏顶栏 app 包名)`——纯内存查表，命中 → "sensitive operation needs user operate" 硬停。
- 模型全程不参与；连"知道"都不会——这是纯系统内部通知机制。
- 策略词表（settings_sens_words/views）另有 ContentObserver 从 securityserver 实时更新。

### 2. 提示词敏感内容检查（checkPrompt / inferPromptRiskType）——【端侧小模型 + 词表 fallback，调用点硬编码】
- 判定器：**AIKernel 端侧模型包 `pico_content_security`**（ContentDetector.kt，DSP/NPU 推理，非对话 LLM、非云端）——输出类别集合；含 "security" 类别 → 放行，否则风险 3。
- fallback（模型不可用时）：**本地词表** wordfilter（`findSensitiveCategories`；词表由 securityserver 经 `content://com.obric.securityserver.settings/.../settings_sens_words` 云端下发）。
- **调用点是硬编码**：任务状态机 QUEUEING 状态必查（session/state/a/k.java），命中 → 任务直接失败（"query includes sensitive content"）。模型（对话 LLM）无法跳过。

### 3. 权限弹窗策略（acquirePermissionStrategy）——【硬编码组件名比较 + 框架 API 取数 + 硬编码映射表】
- 检测：**字符串精确比较** 虚拟屏 topActivity：
  - `com.android.permissioncontroller.permission.ui.GrantPermissionsActivity` → 权限弹窗；
  - `com.android.launcher3.dragndrop.AddItemActivity` → 直接 DENY（桌面添加组件）。
- 数据：framework binder API `getCurrentAppGrantPermissionInfo(pkg)`（经 `android.security.obric.guard.ObricSecurityGuardStub` 反射调用）→ system 侧 `MinPermissionManager` 返回当前弹窗的权限名/等级(deny|oneTime|duringUse|always)/用途说明。该数据由 ROM 定制的 permissioncontroller **在弹窗出现时写入**（LRU 缓存 + min_per_policy.json 持久化）。
- 建议策略映射：**硬编码权限组映射表**（CAMERA/CONTACTS/CALENDAR/MIC → DURING_USE，位置 → DURING_USE...；云开关 `vlm.security.default_strategies` 可关闭默认表）。
- 效果：策略为 DENY/需要授权时 → "permission grant needed" → 停止，agent 不代替用户点"允许"。

### 4. 页面操作策略（acquirePageOperationPolicy → SensitiveViewDetect）——【纯代码查表】
- 判定：`包名/Activity名` 字符串精确匹配两个集合（system 侧 SensitiveViewDetect，策略文件云端下发至 /data/misc/security/guard/）：
  - `free_payment` 集 → 风险 2（免密支付页）→ **硬停**（"accessing free payment page"）；
  - `maybe_free_payment` 集 → 风险 10（疑似）→ 提示文案。
- 经 framework stub `getActivityRiskType(pkg, activity, extra)` 暴露给插件。

### 5. 应用黑名单——【代码比较，数据三方合成】
- 服务端任务响应下发 hard_blacklist/soft_blacklist 数组 + 用户授权开关（Keva）+ OS 约束列表 → 代码逐包名比较；硬黑名单命中抛异常终止，软黑名单走 CLARIFY 问询卡片。

### 6. AGRP robots 策略——【代码读 provider + 代码比较】
- 每次截图/操作前 `refreshRobotsPolicyBeforeScreenshot(顶部组件)` → 查 `content://com.obric.agentrobots.provider/policy` → 比较合并后的 global/screenshot/input_disable 三布尔 → Invisible/Inoperable。页面级与应用级取最严。

### 7. FLAG_SECURE 安全页——【系统 API】
- 截图结果 `ScreenCaptureHardwareBuffer.containsSecureLayers()`（系统 API）→ ContainsSecure 状态，拒绝感知。

### 8. 防伪造用户点击——【系统侧物理事件指纹匹配】
- system_server 记录物理触摸 DOWN/UP 指纹；ViewTree 点击上报必须 `matchUpEventId(fingerprint)` 命中真实物理事件才转发。注入事件无物理指纹 → 无法冒充"用户真实点击"。

### 9. loopGuard 防失控——【代码计数】
- 同能力操作重复 ≥5 告警、≥10 阻断（`js.script.same_ability_loop_block_threshold`，云可配）。

### 10. 步效校验——【代码像素比较】
- `checkPixelsChanged/checkChangedBetweenSteps`：操作前后截图像素差异检测（判断步是否生效/白屏 isInWhiteScreen）。

### 11. intent 认证策略（AuthenticationProcessor）——【代码策略表 + KeyguardManager 状态】
- intent_execute.json 表（云端签发更新）+ `KeyguardManager.isDeviceLocked/isKeyguardLocked`（系统 API）+ 会话认证缓存（内存 StateFlow）三输入，代码计算 policy type 0-4。模型不参与。

## 判定主体分类总表

| 门禁 | 判定主体 | 信号 | 模型可否影响 |
|---|---|---|---|
| 敏感设置操作 | **代码**（系统埋点通知） | 23 种硬编码事件枚举，系统应用 binder 上报 | 否（完全不知情） |
| 提示词敏感内容 | **端侧小模型 pico_content_security** + 词表 fallback | 文本输入 | 否（对话 LLM 无法跳过；调用点硬编码） |
| 权限弹窗 | **代码**（组件名比较 + 框架取数 + 硬编码映射） | GrantPermissionsActivity 组件名；框架 API 权限信息 | 否 |
| 免密支付页 | **代码查表** | pkg/activity 精确匹配云端下发表的 | 否 |
| 应用黑名单 | **代码比较** | 服务端数组+用户开关+OS 列表 | 否（服务端自身可改） |
| AGRP robots | **代码读 provider** | 应用/OEM 声明的策略 | 否 |
| FLAG_SECURE | **系统 API** | containsSecureLayers | 否 |
| 点击防伪 | **系统侧指纹匹配** | 物理触摸事件 | 否 |
| loopGuard | **代码计数** | 操作历史 | 否 |
| 认证策略 | **代码策略表** | JSON 表+锁屏状态+会话缓存 | 否（o_skip_authentication 是服务端开关） |

**唯一"模型判断"的部分**：对话内何时发起 System_UserConfirm/AskUser（服务端提示词决策）、Omni 执行中的 CallUserStep 时机（服务端 Omni 模型决策）——但这些是"主动询问"，不是"拦截"；拦截层全部如上表，与模型无关。

## 审查后补充：门禁的覆盖范围（关键限定，实测发现）

上表各门禁"判定与模型无关"成立，但**守护范围有边界**，三者并不等价：

| 路径 | 经过 AuthenticationProcessor | 经过 autogui 每步门禁（含敏感事件/权限弹窗/支付页） |
|---|---|---|
| intent 直连（模型默认） | ✅（仅锁屏安全锁时产生认证；解锁态放行） | ❌ **完全不经过** |
| GUI 自动化 | ✅ | ✅ |

且敏感事件门禁还要求**目标 app 已埋点**：settings/mms/contacts/filemanager 已埋（contacts 的删除在 GUI 路径确实会被拦在系统确认框前）；**com.obric.notes 未埋点**（GUI 删除也不设防）。

**实测结论（2026-10-16 复核修正）**：
- 删联系人 ×2 → **两次端侧零执行痕迹、联系人始终未删**（推断服务端拦截了工具调用下发）；第一次回复**谎报"已删除"**、第二次如实回复"没有权限"。端侧代码虽无确认门禁（ContactsDeleteIntent 直调删除服务是静态事实），但实际执行从未发生——**真实防线在服务端**，且模型回复与实际状态可能不符。
- 删联系人（GUI 路径，若发生）→ 系统确认框留给用户（EVENT_START 先于对话框上报，agent 点"确认"步骤会被硬拦）——静态代码事实。
- 删便签 → **零确认且真实删除**（GUI 路径，app 未埋点，事后打开便签 app 复核列表为空）。

即：**"删除必问"不存在代码级保证；实际拦截行为是分层的**——服务端（联系人，行为不稳定）、GUI 事件门禁（埋点 app）、无任何拦截（便签）。回复文本不能作为执行凭证。
