# 任务派发后的安全检查 —— 工具调用路径 与 GUI 操作路径

> **范围约定**（按需求聚焦）：用户已派发任务；**假设 per-app 授权已全部开启**；不讨论风险偏好（软参数）、不讨论锁屏/声纹/生物认证。只回答：模型决定执行后，端侧在**①工具调用（intent 直连）**和**②GUI 自动化（虚拟屏操作）**两条路径上各做哪些安全检查、用什么数据判、在哪里拦。
> 源码路径缩写：`P:`=`decompiled/aiagent_plugin/sources`，`H:`=`decompiled/larus_nova*/sources`，`OS:`=`decompiled/obric_services/sources`，`SS:`=`decompiled/securityserver/sources`，`CT:`=`decompiled/contacts_app/sources`。完整策略表 JSON：`apks/extracted_aiagent_plugin/assets/security_policies/intent_execute.json`。

## 结论总览

| | ① 工具调用路径（intent 直连） | ② GUI 操作路径（autogui 虚拟屏） |
|---|---|---|
| 检查点数量 | **1 个**（策略表→解锁态下全部放行） | **任务级 2 个 + 每步 5 个 + 全程 3 个** |
| 内容级拦截（看任务/页面内容） | ❌ 无（端侧不看内容） | ✅ 有（敏感内容模型、支付页、敏感事件、权限弹窗、robots） |
| 黑名单/授权 | 端侧不查（授权状态上行，由服务端拒绝——实测微博） | ✅ 每步查（云 hard/soft + 用户授权 + OS 三层合成） |
| 防失控 | ❌ 无 | ✅ loopGuard（同操作 10 次阻断）+ 像素步效校验 |
| 审计 | ✅ 每次执行留痕（Merkle 防篡改） | ✅ 每步留痕（含截图策略快照） |
| **净效果（授权已开+解锁态）** | **端侧零拦截，工具直接在目标 app 进程执行**；真正决定"发不发"的是服务端（实测删联系人两次都未下发，端侧零痕迹） | **端侧多道硬拦，逐项见下** |

# 第一部分：工具调用路径（intent 直连）

模型（服务端）决定调用某工具 → 下发 intent → 端侧 `execIntentAsync` → **AuthenticationProcessor（唯一关卡）** → 反射执行目标 app 注册的 IntentFunction → 结果回传服务端。

## 1.1 唯一关卡：intent 执行策略表

- **源码**：计算与分发 `P:/com/obric/aiagent/executionengine/scheduler/impl/execution/security/a.java`（AuthenticationProcessor.kt，`getPolicyType` 行419-466 / 分发行387-417）；挂载 `P:/.../scheduler/impl/a/d.java` 行1118+（`execIntentAsync` 内强制调用，非 IntentParams 类型才豁免——业务 intent 全是 IntentParams）；AppFunction 同样过检 `P:/.../scheduler/impl/b/c.java` 行214（默认策略 appfunc_execute=type4）。
- **数据**：161 条策略（云端 `obric_appintent_lockscreen_execute_config` 优先、须字节签名；assets 兜底）。**完整 161 条表见附录 A**。
- **type 语义**：0=放行；1=需认证；2=仅声纹；3=生物/凭证；4=仅需亮屏；**表里没有的 intent → 默认 type3**（行462：`return 3`）。
- **本范围（解锁态）下的实际效果**：type1-3 的认证分支只在"安全锁屏"时才产生交互（`isDeviceLocked==false` → 直接 return null 放行，行732/753）；type4 只在灭屏时要求亮屏。**→ 解锁态下全部 type 都放行，策略表不产生任何拦截。**
- 两个例外豁免即使在锁屏也值得知道：Omni 复杂任务整体豁免（`System_UserAuthorize`、`Doubao_RealTimeScreenShare` 除外，行1168-1187）；服务端可随消息下发 `o_skip_authentication=1` 直接跳过（行1189-1197）。

## 1.2 端侧不再有任何其他检查

- **不查授权/黑名单**：per-app 授权状态（`o_automatic_execution_authorization`）是上行给服务端的上下文；未授权时是**服务端拒绝下发**（实测：撤销微博授权 → 模型直接回"没有权限"，端侧零执行痕迹）。
- **不看任务内容**：敏感内容检查（pico 模型）只挂在 GUI 任务队列（见第二部分），intent 直连不经过。
- **目标 app 的 intent 实现各自定义**，多数无自检：例——`CT:/com/obric/appintents/contacts/ContactsDeleteIntent.java` `deleteContacts()` 直调 `ContactSaveService.createDeleteRawContactIntent` 删除，无对话框无二次确认（行66-98）。**工具调用一旦下发，破坏性操作在端侧无缓冲。**

## 1.3 每次执行强制留痕（审计）

- `OS:/com/obric/server/security/audit/SecurityAuditManagerService.java`：`recordAuditWithResult`（行113+）写 `/data/system/security_audit/agent_robots/audit.db`（Merkle 树防篡改，`MerkleIntegrityManager.java`）；写前校验 agentUuid=SHA256(agentName+pkg+rootCertHash) 须在硬件注册表内（行254-281、372-433）。实测 logcat 可见 `recordAudit allow: agentUuid is registered`。
- 任务结束审计含服务端的输入/输出安全检查结论：`P:/com/obric/agent/trace/omni/l.java` 行95-139（`check_user_input_audit_info`、`check_llm_output_audit_info` 字段入审计）。

## 1.4 该路径的真实风险面（实测）

服务端两次都没把"删除联系人"下发执行（端侧零痕迹），但第一次模型**谎报"已删除"**、第二次如实说"没有权限"——**下发与否的最终决定在服务端，端侧无从验证，且回复文本可能与事实不符**。

# 第二部分：GUI 操作路径（autogui 虚拟屏）

任务进入 Omni 引擎 → **任务级检查** → 创建虚拟屏 → 服务端逐步下发动作 → **每步 5 连检** → 注入执行 → **步效校验**。

## 2.0 任务级检查（进入队列时，各一次）

### 检查① 任务提示词敏感内容（本地小模型）
- **逻辑**：用**端侧模型包 `pico_content_security`**（AIKernel DSP/NPU 推理）对任务文本推理；命中敏感类别 → 任务直接失败（"query includes sensitive content"）；模型不可用时 fallback 词表匹配。
- **源码**：调用点（硬编码在状态机 QUEUEING 态）`P:/com/obric/autogui/session/state/a/k.java` 行222-244；推理器 `P:/com/bytedance/securityguardkit/SecurityGuardKitManager.java`（inferSensitiveContent 行105+，模型初始化 `.../securityguardkit/b/b.java` ContentDetector，模型包名见行563 `pico_content_security`）；词表 fallback `.../wordfilter/{a,b}.java`。
- **词表数据**：云端经 `content://com.obric.securityserver.settings/policy_version/settings_sens_words` 下发（`.../settingsevent/SettingsPolicyObserver.java` 行52）；真值存 `/data/misc/security/guard/`（**无 root 不可读；provider 查询被拒——内容为运行时云端数据，非写死**）。

### 检查② 黑名单注册（服务端下发）
- **逻辑**：任务创建响应携带 `hard_blacklist[]`/`soft_blacklist[]` → 端侧 `OperatingSpaceManager.setGlobalDisabledApps` 全局禁用；每步命中见检查⑤。

# 【第三轮实测修订 2026-10-16 晚】每步 5 连检的适用范围修正（重大）

通过字节码级交叉引用（androguard 全 dex 扫描）+ 删除联系人 GUI 实验（logs/cs0-cs2.png）+ 逐指令级 logcat 输入事件还原，发现并确认：

## 修正：敏感设置操作检测（S-10）只挂在"脚本路径"，不挂在 Omni 主路径

**原始推理错误**：我此前把"每步 5 连检"（e/c/f.java 的 SecurityCheck）当成所有 GUI 步骤的通用前置。字节码 xref 证明它**只被一个类调用**：

- **安全检查接口** `e/c/e.a(Context, session, String, cont)` 的**全插件唯一调用点** = `e/b/e`（StepExecutor）
- **StepExecutor(e/b/e) 的构造点全插件唯一** = `l.java`（StandardModelScriptStep，脚本执行步骤）
- **SecurityCheck 实现(e/c/f) 的实例化点全插件唯一** = 同上 `l.java` 构造器
- **Omni/StandardModel 主执行链**：`session/c.c(session)` → **直接调** `operator/e.b(session)` 执行步骤——**不经过 StepExecutor、不经过安全检查**

即：
```
脚本路径（能力脚本，如"打开XX app"已知流程）:
  d/f 解析 → d/e ScriptStepParser → l (ScriptStep) → e/b/e StepExecutor → ✅ e/c/f 五连检 → 执行

Omni 主路径（服务端 VLM 逐步下发，即"手机任务"的实际执行方式）:
  d/f 解析 → ActionedStep(e)/其他步骤 → session/c.c() → step.b() → ❌ 直接执行（无每步安全检查）
```

**实测验证（删除联系人 GUI 实验）**：
- 20:51:00 虚拟屏 display 120 创建；20:51:02 观察者注册成功（"registerSettingsEventObserver, packageName:com.larus.nova"）
- Agent 逐步操作（InputDispatcher 记录 display 120 全部注入点）：20:51:56 打开联系人 → 20:52:00 点搜索框(441,434) → 20:52:12 点结果(352,448) → 20:52:15 点更多(1147,238) → 20:52:19 点删除(756,784)
- **20:52:19.23 系统侧 CONTACT_DELETE 事件上报（eventType:2）**——但 3.4 秒后：
- **20:52:22.58 agent 直接点击了确认对话框的"删除"按钮**（注入事件(756,784)→对话框区域）→ **联系人被删除**
- **敏感事件门禁没有拦截确认点击**——因为该门禁只在脚本路径生效，Omni 主路径不检查
- 最终回复还谎称："需要你在手机上确认，已为你打开确认页面"——实际页面已自动关闭且已删除
